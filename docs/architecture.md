# Architecture

This is the living description of how the workspace fits together. Dated
status reports from earlier work are archived under `docs/history/` and are
not kept up to date; open design problems are tracked in
`design-improvements.md`.

## Crates

Arrows point from a crate to what it depends on.

```text
aeon-swarm ──────────────┐
aeon-frontend ───────────┼─> aeon-service ─> aeon ─> aeon-reduce ─> aeonil
aeon-eval ───────────────────────────────────┘│                       ▲
survey ───────────────────────────────────────┘                       │
aeon-instrument ─> aeon-jit ─> aeon, aeon-reduce, aeonil ─────────────┘
```

| Crate | Role |
|-------|------|
| `aeonil` | The IL: `Expr`, `Stmt`, typed intrinsics, and the one definition of integer width (`Expr::int_bits`). No dependencies on the rest of the workspace. |
| `aeon-reduce` | IL-to-IL simplification. Block-local and function-level passes (`pass.rs`, `pipeline.rs`) and an SSA form with its own passes (`ssa/`). Every stage is a table of named passes. |
| `aeon` | The analysis library: ELF loading, lifting, the IL interpreter, per-function artifacts, Datalog analyses, pointer and object-layout recovery, and the `AeonSession` API. |
| `aeon-service` | The stateful tool service: one loaded binary, a typed request per tool, JSON in and out. Knows nothing about transports. |
| `aeon-frontend` | Transports over the service: the `aeon` CLI, MCP over stdio (`aeon-mcp`) and HTTP (`aeon-http`). |
| `aeon-swarm` | Multi-agent orchestrator that drives the service through tool calls. |
| `aeon-jit` | Cranelift backend for the IL: in-process JIT and AArch64 object emission. |
| `aeon-instrument` | Dynamic execution on top of the JIT: tracing, dynamic CFG, snapshots, and the translation binaries. |
| `aeon-eval` | Evaluation corpus, tasks, claims, evidence, and the reduction goldens under `eval/goldens/`. |
| `survey` | Standalone opcode survey utility. |

## From bytes to answers

```text
ELF image                      aeon::elf
  -> bad64 decode
    -> AeonIL                  aeon::lifter
      -> reduced CFG           aeon-reduce (block, function passes)
        -> SSA                 aeon-reduce::ssa
          -> facts             aeon::facts
            -> Datalog         aeon::datalog, aeon::analysis (ascent)
              -> tool call     aeon-service
                -> transport   aeon-frontend (CLI, MCP, HTTP)
```

`AeonSession` (`aeon::api`) owns three things and stores nothing twice:

- the immutable loaded binary;
- a cache of per-function `FunctionArtifacts` (`aeon::function_ir`):
  decoded instructions, reduced CFG, SSA and facts, each computed on demand;
- the `Blackboard` (`aeon::blackboard`) of analyst annotations: names,
  struct definitions, hypotheses.

The session is `Send + Sync`. Errors are `aeon::Error` with an `ErrorKind`;
the service maps them onto tool responses.

## Executing the IL

There are three engines for the same IL:

- the interpreter in `aeon::emulation`;
- the Cranelift JIT in `aeon-jit`;
- Unicorn, running the original machine code, as the reference.

`crates/aeon-jit/tests/differential.rs` runs generated ARM64 cases through
all three and requires identical register, flag and memory state. It also
runs the JIT on the IL after every block-local reducer pass, so a reducer
bug is reported against the pass that introduced it. Cases are generated by
`tests/differential/gen_cases.py` (needs cross binutils).

## The reducer

Each stage is a table whose order is the pipeline order:

- `BLOCK_PASSES` and `CFG_PASSES` in `aeon-reduce/src/pass.rs`;
- `SSA_PASSES` in `aeon-reduce/src/ssa/pipeline.rs`.

A runner per stage applies the table, collects per-pass counts and calls an
observer after each pass. `optimize_ssa_validated` checks SSA validity
after every SSA pass.

## Where to add things

- A new instruction: lift it in `aeon::lifter`; if it needs a new IL node,
  add it to `aeonil` and teach the interpreter and the JIT lowering; add a
  case to `gen_cases.py`.
- A new reducer pass: write it in `aeon-reduce` and add a row to the
  relevant table.
- A new tool: add its request type to `aeon-service/src/requests.rs` and its
  handler to `service.rs`; every transport picks it up. Regenerate the
  README tool table with `cargo run -p aeon-frontend --bin aeon_docgen`.
